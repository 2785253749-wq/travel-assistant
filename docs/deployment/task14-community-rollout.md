# 社区功能部署与回滚

## 部署前检查

1. 确认后端环境配置了 `SUPABASE_URL`、`SUPABASE_ANON_KEY`、`SUPABASE_SERVICE_KEY` 和有效的会话签名密钥。
2. 确认 `SUPABASE_SERVICE_KEY` 只存在于后端部署环境；不写入静态资源、`runtime-config.js`、HTML 或浏览器环境变量。
3. 在目标 Supabase 项目检查迁移记录，只执行尚未应用的迁移，顺序固定为 `010`、`011`、`012`。已应用的迁移跳过，不重复执行。
4. 不执行删除表或删除 RPC 的 down migration。

## 发布顺序

1. 备份目标环境迁移记录和应用配置，不备份或输出明文密钥到日志。
2. 运行迁移状态检查，并仅补齐尚未应用的 `010 → 011 → 012`。
3. 部署后端，使公开 RPC、互动 RPC、审核 RPC 和签名媒体路径与数据库版本兼容。
4. 部署静态资源和前端页面。
5. 执行冒烟检查：匿名公开列表/详情、账户 A/B 私有隔离、已审核评论、管理员三类队列、签名图片预览、举报关闭和 service-role 前端泄露检查。

## 回滚

- 应用代码异常时，回滚应用版本，保留已应用的 `010`、`011`、`012` 表、索引和 RPC；新旧版本必须继续使用向后兼容的新增结构。
- 不通过删除表、删除 RPC 或逆向迁移来回滚数据结构。
- 若发现权限或数据异常，先暂停相关写入并保留审计记录，再使用明确的管理员操作或前向修复迁移处理。
- 举报 `actioned` 只代表关闭举报和记录决定，不作为隐藏游记或评论的替代操作。
- 仅在确认旧应用不再依赖新字段且完成数据核对后，才恢复流量；恢复后重复执行匿名、双账户和管理员冒烟检查。

## 安全检查

- 日志只允许哈希主体、请求 ID、稳定错误码和操作阶段。
- API 响应不得返回邮箱、完整内部 UUID、Storage 路径、令牌或私有行程字段。
- 审核队列图片只能返回短期签名 URL。
