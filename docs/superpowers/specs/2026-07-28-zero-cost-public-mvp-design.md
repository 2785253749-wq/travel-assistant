# 旅行助手零成本公开 MVP 设计

日期：2026-07-28

## 1. 目标与约束

在现有 FastAPI、LangGraph 和 DeepSeek 原型基础上，用 8 周、约 220～240 小时完成一个可公开访问的旅行规划 MVP。

项目约束如下：

- 开发者为 1 人，每天投入至少 5 小时，每周按 6 个开发日规划。
- 托管、数据库、地图、天气等平台月费必须为 0 元。
- 接受免费服务的休眠、冷启动、二级域名、流量限制和临时停服。
- 继续使用项目维护者现有的 DeepSeek API Key；模型调用费不属于平台月费，必须通过每日限额、总额熔断和手动停服控制。
- 不购买机票、酒店或铁路商业数据接口。
- 不执行支付、预订、出票、退改签或任何真实交易。
- 机票、酒店和火车仅提供搜索条件与第三方平台跳转，并明确提示以第三方实时信息为准。

### 1.1 垂直场景定义

本项目只服务“国内多日自由行的行前规划”，不做通用聊天机器人。

- **谁使用**：预算敏感、缺少行程规划经验的学生和年轻自由行用户，典型行程为国内 2～7 天、1～6 人。
- **使用场景**：用户已经有初步出行想法，但尚未整理日期、人数、预算、兴趣和交通住宿选择，需要在预订前形成可执行方案。
- **核心痛点**：旅行信息分散；用户描述不完整；景点堆砌导致路线不合理；总预算无法落实到交通、住宿、餐饮和门票；AI 容易编造实时价格、余票和营业时间。
- **解决办法**：通过多轮对话补齐必要信息，使用结构化状态生成逐日路线和预算；对免费外部数据标注来源和时间；信息不足时追问，超出能力或无法核实时明确拒答；机票、酒店和火车只提供搜索入口。
- **成功结果**：目标用户能在 10 分钟内，从一句不完整需求得到一份经过确认、可保存、可分享且不冒充实时预订信息的国内自由行方案。

## 2. MVP 功能范围

### 2.1 用户与账号

- 支持邮箱注册、登录和退出。
- 用户只能读取、修改和删除自己的旅行数据。
- 未登录用户可以体验临时会话，但不能跨设备保存。

### 2.2 旅行需求收集

- 多轮收集出发地、目的地、出发日期、返回日期、人数和总预算。
- 可选收集兴趣、饮食、住宿、交通、无障碍需求和其他限制。
- 对日期顺序、人数、预算和文本长度执行服务端校验。
- 在生成规划前展示结构化资料，允许用户修改确认。

### 2.3 行程生成与管理

- 生成行程摘要、预算分配、每日早中晚安排、城市内交通建议、预订清单、风险和待确认事项。
- 行程以结构化数据存储，同时保留适合阅读的 Markdown 内容。
- 支持保存、重命名、复制、删除、历史查看和重新生成。
- 分享功能使用不可猜测、可撤销的只读令牌，不公开聊天记录和用户信息。

### 2.4 免费旅行信息

- 天气、地图和景点通过独立 provider 接口获取，具体供应商可替换。
- 外部数据需要显示来源、获取时间和“仅供参考”提示。
- 外部接口不可用时，仍返回不依赖实时数据的基础 AI 行程。
- 机票、酒店和火车只生成搜索条件与外部搜索链接，不展示伪造的实时价格、库存或余票。

### 2.5 成本与滥用控制

- 对匿名用户、登录用户和 IP 设置不同的请求速率限制。
- 为 DeepSeek 设置单用户每日调用数、全站每日调用数和管理员总开关。
- 达到限额时返回清晰提示，不继续调用收费模型。
- 日志记录请求编号、耗时、状态和令牌用量，不记录 API Key、密码或完整敏感对话。

## 3. 系统架构

### 3.1 应用结构

保留 Python 单体应用以控制开发成本，但在内部按职责拆分：

- `app/api/`：HTTP 路由、认证依赖和响应映射。
- `app/agent/`：LangGraph 状态、需求提取、路由和规划节点。
- `app/trips/`：行程领域模型、服务和存储接口。
- `app/providers/`：天气、地点和外部搜索链接适配器。
- `app/core/`：配置、日志、异常、限流和 DeepSeek 用量控制。
- `app/static/`：浏览器端页面、样式和交互脚本。

模块间通过明确的数据模型和服务接口通信。API 层不直接拼接模型提示词，Agent 层不直接操作数据库，外部数据调用只能经过 provider 接口。

### 3.2 托管与数据

- FastAPI Web Service 部署到 Render 免费实例，使用平台二级域名和 TLS。
- Supabase 免费项目提供 Postgres、邮箱认证和行级安全策略。
- Render 文件系统只存临时内容，不使用 SQLite 保存生产数据。
- DeepSeek Key、Supabase 服务端密钥和管理员开关只存部署平台 Secret。
- 免费服务政策变化时，部署实现可以替换，但应用接口保持不变。

### 3.3 核心数据实体

- `profiles`：用户展示信息和偏好。
- `trips`：行程标题、状态、结构化需求、规划结果、创建与更新时间。
- `conversation_messages`：必要的用户消息与助手最终回复；不保存模型思考过程。
- `share_links`：哈希后的分享令牌、行程 ID、过期时间和撤销时间。
- `ai_usage`：用户、日期、调用次数、令牌数和状态。

所有用户数据表启用 Supabase Row Level Security。分享读取通过独立的受限服务方法完成，不放宽用户表策略。

## 4. 完整处理流程

1. **接收请求**：浏览器提交消息、会话标识和可选登录身份。
2. **入口校验**：API 验证文本长度、身份、速率、AI 配额和请求编号；失败时不进入 Agent。
3. **意图识别**：将请求分为 `plan_trip`、`modify_trip`、`explain_trip`、`smalltalk`、`unsupported` 五类，并记录分类置信度。
4. **场景路由**：
   - `plan_trip` 进入需求收集；
   - `modify_trip` 必须存在可修改的行程，否则提示用户先创建或选择行程；
   - `explain_trip` 只能解释已经生成的方案，不扩展未核实的事实；
   - `smalltalk` 简短回应并引导回国内自由行规划；
   - `unsupported` 明确说明能力边界并拒绝处理。
5. **字段提取**：从最新消息提取出发地、目的地、日期、人数、预算、偏好和限制，并与已确认资料合并。
6. **完整性与一致性检查**：检查必填字段、日期顺序、人数、预算和目的地是否适合本项目场景。
7. **追问或拒答**：
   - 缺少关键信息时只追问缺失字段，不生成完整行程；
   - 信息互相矛盾时要求用户确认，不自行选择；
   - 用户索要实时价格、余票、签证结论、医疗或安全保证时拒绝给出确定答案，并提供官方核实入口；
   - 外部事实没有来源或已超过允许缓存时间时标记“无法核实”，不得让模型补全。
8. **资料确认**：在首次完整规划前向用户展示结构化资料，用户确认或修改后才继续。
9. **外部信息获取**：并行请求可用的天气与地点 provider，记录来源、获取时间、超时和降级状态。
10. **行程生成**：Agent 只使用已确认资料和可追溯外部数据，生成结构化行程、预算和免责声明。
11. **输出验证**：校验 JSON Schema、日期覆盖、预算合计、每天时间段、引用来源和禁用声明；失败时最多自动修复一次，仍失败则返回安全错误。
12. **保存与响应**：保存行程、最终回复和用量记录；浏览器渲染来源、更新时间、外部搜索链接和免责声明。

## 5. 错误处理与安全

- 配置缺失在应用启动时报告，不在首个用户请求时才失败。
- 外部 API 设置连接与总超时、有限重试和短时缓存。
- DeepSeek 的限流、余额不足、响应解析失败分别映射为可理解的用户提示。
- 所有公开错误响应包含请求编号，但不暴露堆栈、密钥、数据库语句或供应商原始响应。
- 分享令牌只存哈希值，默认有效期 30 天，并允许用户随时撤销。
- `.env`、虚拟环境、缓存、日志和本地数据库永不提交 Git。
- GitHub 提交前运行敏感信息扫描，并检查 Git 跟踪文件列表。
- 配置按开发、测试、生产环境分层，所有配置项通过 Pydantic Settings 校验；`.env.example` 列出变量名、用途和安全默认值。
- 日志采用 JSON 结构，至少包含时间、级别、请求编号、用户匿名标识、路由、意图、耗时、供应商状态、模型用量和错误类型。
- 每次请求把同一 `request_id` 贯穿 API、Agent、provider 和数据库操作，便于定位端到端故障。

## 6. 量化评估与优化闭环

### 6.1 评测集

建立 80 条版本化测试用例，保存在 `tests/evaluation/cases.jsonl`，每条包含输入、历史上下文、预期意图、预期字段、是否应追问或拒答，以及允许出现的事实来源。

- 20 条完整旅行规划请求，覆盖不同城市、日期、人数和预算。
- 20 条信息缺失或前后矛盾请求，覆盖多轮补充和修改。
- 15 条超出范围或必须拒答请求，覆盖实时价格、余票、签证、医疗、安全保证和真实预订。
- 15 条口语、错别字、模糊表达和上下文指代请求。
- 10 条外部服务超时、空结果、模型格式错误和配额耗尽异常用例。

评测集中的固定事实不依赖持续变化的实时价格；需要外部数据的用例使用可重复的 provider fixture。

### 6.2 指标与发布门槛

| 指标 | 计算方式 | MVP 门槛 |
|---|---|---:|
| 意图识别准确率 | 正确意图数 / 总意图用例数 | ≥ 90% |
| 关键字段 Micro-F1 | 出发地、目的地、日期、人数、预算的综合 F1 | ≥ 90% |
| 追问命中率 | 信息不足时正确追问 / 应追问用例数 | ≥ 95% |
| 拒答召回率 | 正确拒答 / 必须拒答用例数 | ≥ 95% |
| 拒答精确率 | 正确拒答 / 全部拒答数 | ≥ 90% |
| 结构化输出有效率 | 通过 JSON Schema 校验的规划数 / 规划请求数 | ≥ 98% |
| 无依据事实率 | 无来源且被表述为确定事实的条目 / 全部事实条目 | ≤ 2% |
| 端到端任务成功率 | 完成正确路由、追问/拒答和最终响应的用例数 / 80 | ≥ 85% |
| 异常兜底成功率 | 返回预期安全提示且无未处理异常 / 异常用例数 | 100% |

另外记录 P50/P95 响应时间、单次规划输入输出令牌数和 DeepSeek 估算费用，但免费服务冷启动时间单独统计，不与热启动混合。

### 6.3 指标驱动优化

- 意图准确率低：补充混淆用例，调整意图定义、示例和路由提示，不直接增加更多 Agent 节点。
- 字段 F1 低：规范日期、金额和人数的解析前处理，并为易混字段增加结构化示例。
- 追问命中率低：把缺失字段判断从生成提示中抽离为确定性代码。
- 拒答召回率低或幻觉偏高：增加禁止声明、来源白名单和输出后事实检查；没有来源的事实降级为待确认事项。
- 地点检索命中率低：记录失败 query，执行城市限定、别名归一化和 query 重写，再重试一次。
- 输出有效率低：缩小 Schema、降低单次输出复杂度，并保留一次结构化修复机会。
- 异常兜底失败：为对应供应商错误建立稳定错误码、fixture 和回归用例。

每次修改提示词、模型、provider 或路由规则后运行同一评测集，保存版本、指标和变更说明。只有目标指标不下降且相关缺陷指标提升，优化才能进入主分支。

## 7. 测试与验收

### 7.1 自动测试

- 单元测试：资料合并、字段校验、预算分配、配额和 provider 降级。
- Agent 合约测试：使用假模型验证状态路由和结构化输出，不消耗真实 API。
- API 集成测试：认证、数据隔离、行程 CRUD、分享和错误映射。
- 部署冒烟测试：首页、健康检查、登录、一次多轮规划和只读分享。
- 安全测试：越权读取、过长输入、恶意分享令牌、限流和日志脱敏。
- 评测测试：80 条用例可通过单条命令运行，并输出 JSON 与 Markdown 两种报告。

### 7.2 发布验收标准

- 新用户能注册、登录，并在 10 分钟内完成首个旅行方案。
- 服务重启后用户仍能查看历史行程并继续修改。
- 用户无法通过 ID 或分享接口读取他人的私有行程。
- 天气或地点服务失败时，核心规划仍可完成并显示降级提示。
- 达到 DeepSeek 限额后不再产生模型调用。
- 仓库和部署日志中不存在真实 API Key。
- 手机和桌面浏览器均能完成登录、规划、保存和分享流程。
- 80 条评测集达到第 6.2 节全部发布门槛，报告随版本保存。
- 任意请求可以通过 `request_id` 在结构化日志中还原入口、意图、Agent、provider 和响应结果。

## 8. 八周开发周期

| 周次 | 计划投入 | 主要交付 | 周末验收 |
|---|---:|---|---|
| 第 1 周 | 28～30 小时 | 垂直场景、意图与拒答边界、工程目录、配置分层、结构化日志、数据库设计 | 本地一键启动，配置启动校验与请求链路日志通过 |
| 第 2 周 | 28～30 小时 | Supabase 项目、注册登录、用户表、行程 CRUD 与 RLS | 两个测试账号的数据完全隔离 |
| 第 3 周 | 28～30 小时 | 意图路由、Agent 模块拆分、会话持久化、字段确认、追问与拒答 | 重启后继续会话，缺信息不生成，越界请求正确拒答 |
| 第 4 周 | 28～30 小时 | 结构化行程、预算模块、重新生成与版本保存 | 固定用例稳定输出合法结构和预算 |
| 第 5 周 | 28～30 小时 | 天气、地点 provider、缓存、降级、交通住宿搜索链接 | 断开外部服务仍能生成基础方案 |
| 第 6 周 | 28～30 小时 | 响应式前端、历史列表、编辑、删除和只读分享 | 手机与桌面完成核心用户旅程 |
| 第 7 周 | 28～30 小时 | 80 条评测集、指标报告、针对性优化、用量限制和全站熔断 | 全部量化指标达到发布门槛，超限后零额外模型请求 |
| 第 8 周 | 25～30 小时 | 全量回归、安全检查、Render 部署、README、评测与演示文档 | 发布验收标准全部通过并生成公开版本 |

每周保留约 10% 时间处理未知问题。若外部平台申请或审核延期，优先使用假 provider 完成接口和界面，不阻塞主流程。

## 9. 明确不做的内容

- 实时机票、酒店、铁路价格和库存。
- 站内预订、支付、出票、退款和客服履约。
- 原生 Android、iOS 或微信小程序。
- 多语言、多币种、社交关注、推荐流和商业广告。
- 企业级 SLA、自动扩容、付费域名和付费监控。

上述能力必须在 MVP 获得稳定用户和预算后重新立项，不能暗中扩入本周期。

## 10. GitHub 与交付物

公开仓库名为 `travel-assistant`，默认分支为 `main`。仓库包含源代码、测试、`.env.example`、README、设计文档、实施计划、API 成本调研、评测集、版本化指标报告和免费部署说明。

`.env`、`.venv`、缓存、日志、数据库文件和任何真实凭据均被忽略。首次发布前检查 Git 跟踪列表和敏感模式，确认公开范围后再推送。
