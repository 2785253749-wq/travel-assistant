# Voyage 图文旅行社区产品策划书

日期：2026-08-21
状态：产品方向已确认，待实施计划
范围：图文游记、瀑布流发现、内容审核、首阶段互动及后续完整社交路线

## 1. 背景与问题

当前社区围绕“选择已规划行程、填写摘要、发布公开快照”设计，页面同时放置发布表单、列表和详情，因此更像行程管理后台，不符合用户期望的旅行内容社区。

新版社区应以图片和游记内容为第一视觉对象，形成“发现灵感、阅读内容、互动、创作、审核、公开展示”的产品闭环。私有行程可以成为游记的可选附件，但不再是发布游记的前置条件。

现有 `community_posts` 和 migration 010 保留归档，不删除数据，也不进入新版社区公开列表。新版社区使用独立数据模型和接口，避免把行程快照与图文游记长期混在同一领域模型中。

## 2. 产品定位

Voyage 社区定位为“旅行灵感发现与图文分享社区”。

核心价值：

- 浏览者通过高质量图片、地点和主题分类快速发现旅行灵感。
- 创作者无需先规划行程即可发布独立图文游记。
- 已有 Voyage 行程可作为游记的可选攻略附件。
- 所有公开内容经过人工审核，保证首阶段内容质量。
- 社交能力分阶段建设，避免关注、通知和私信同时开发。

## 3. 目标用户与核心场景

### 3.1 浏览者

- 按最新发布浏览瀑布流。
- 按分类筛选内容。
- 按地点或标题搜索游记。
- 查看图片、正文和可选行程攻略。
- 登录后点赞、收藏和评论。

### 3.2 创作者

- 上传 1–9 张图片并调整顺序。
- 填写标题、正文、地点和单一分类。
- 可选关联一条自己的已规划行程。
- 保存草稿、预览、提交审核。
- 查看待审核、已通过和已驳回内容及驳回原因。

### 3.3 管理员

- 在独立审核页查看待审核游记和评论。
- 查看完整图片、正文、地点、分类及关联行程摘要。
- 通过或驳回内容；驳回必须填写原因。
- 查看审核人、审核时间和历史决定。

## 4. 产品原则

- 内容优先：社区首页只负责发现内容，不并排展示发布表单和详情面板。
- 图片优先：瀑布流卡片首先展示真实封面图，不使用行程数据伪装图文内容。
- 独立创作：图文游记是主内容，行程仅为可选附件。
- 先审后发：游记和评论审核通过后才对其他用户公开。
- 最小公开：公开接口只返回页面需要的字段，不暴露邮箱、作者 UUID、存储路径或私有行程数据。
- 分阶段社交：首阶段完成互动闭环，后续依次增加关注、通知和私信。

## 5. 首阶段内容模型

一篇游记包含：

- 1–9 张图片，首图为默认封面，作者可拖动排序。
- 标题：1–60 个字符。
- 正文：1–5000 个字符，首阶段使用纯文本分段，不引入富文本编辑器。
- 地点：1–80 个字符。
- 一个固定分类。
- 可空的关联行程 ID，只允许关联作者自己的已规划行程。
- 作者公开昵称、头像和发布时间。
- 草稿、待审核、已通过、已驳回四种主要状态。

固定分类：

- 摄影控
- 美食地图
- 独自旅行
- 城市漫步
- 自然风光
- 亲子游

自由标签、视频、地图发现和多分类不进入首阶段。

## 6. 信息架构与页面

### 6.1 社区首页

- 顶部保留主导航和搜索框。
- 分类胶囊依次为“全部”和六个固定分类。
- 默认按审核通过时间倒序排列。
- 搜索范围为地点和标题。
- 桌面端四列瀑布流，平板两列，手机单列。
- 卡片展示封面、地点、标题、作者头像、昵称、点赞数和评论数。
- 卡片点击进入独立详情页；点赞可以直接在卡片完成。
- 使用“加载更多”游标分页，首阶段不使用自动无限滚动。
- 右下角提供悬浮“＋”发布入口。

### 6.2 游记详情页

- 顶部为图片画廊，支持左右切换和缩略图。
- 展示标题、地点、分类、作者、正文和发布时间。
- 展示点赞、收藏、评论和举报入口。
- 关联行程存在时，在正文后展示“查看行程攻略”。
- 作者本人可编辑或删除；编辑已通过游记后内容重新进入待审核，审核期间暂时下线。
- 所有用户文本以纯文本方式渲染，不使用不受控 HTML。

### 6.3 发布与编辑页

发布流程分为：

1. 上传并排序 1–9 张图片。
2. 填写标题、正文、地点和分类。
3. 可选关联自己的已规划行程。
4. 预览瀑布流卡片和详情效果。
5. 保存草稿或提交审核。

页面离开前若有未保存修改，应提示用户；重复提交按钮在请求完成前禁用。

### 6.4 我的游记

- 分组显示草稿、待审核、已通过和已驳回内容。
- 驳回内容显示审核原因，并允许修改后重新提交。
- 已通过内容可编辑、删除或查看公开详情。
- 首阶段作者主页只读，展示头像、简介和已通过游记。

### 6.5 管理员审核页

路径为 `/admin/community`，仅管理员可访问。

- 默认显示待审核队列，支持游记和评论类型筛选。
- 支持通过、驳回及填写审核备注。
- 驳回必须填写面向作者的原因。
- 审核操作写入不可由普通用户修改的审计记录。
- 前端隐藏入口只是体验措施，API 和数据库必须再次验证管理员权限。

## 7. 核心用户流程

### 7.1 内容发现

`进入社区 → 选择分类或搜索 → 浏览瀑布流 → 打开详情 → 点赞/收藏/评论`

匿名用户可以浏览公开内容；进行互动或发布时跳转登录，并保留原返回地址。

### 7.2 内容发布

`登录 → 点击“＋” → 上传图片 → 填写内容 → 预览 → 保存草稿或提交 → 等待审核 → 审核通过后公开`

### 7.3 审核

`管理员打开待审核队列 → 查看完整内容 → 通过或填写原因驳回 → 系统记录决定 → 作者看到结果`

### 7.4 评论

评论提交后，评论者立即看到“审核中”；其他用户只能看到审核通过的评论。管理员在同一审核页处理评论。

## 8. 数据模型

新版社区建议新增 migration 011，并建立以下表：

### 8.1 `travel_notes`

- `id`
- `author_id`
- `title`
- `body`
- `location_name`
- `category`
- `status`
- `source_trip_id`，可空
- `created_at`、`updated_at`
- `submitted_at`、`published_at`
- `deleted_at`，可空

### 8.2 `travel_note_images`

- `id`
- `note_id`
- `owner_id`
- `storage_path`
- `sort_order`
- `width`、`height`
- `created_at`

`(note_id, sort_order)` 唯一，排序第一张为封面。

### 8.3 互动表

- `travel_note_likes`：`(user_id, note_id)` 唯一。
- `travel_note_bookmarks`：`(user_id, note_id)` 唯一，收藏关系私有。
- `travel_note_comments`：正文、作者、审核状态和发布时间。
- `travel_note_reports`：对象类型、对象 ID、举报原因和处理状态。

### 8.4 审核与角色

- `moderation_decisions`：对象、审核人、决定、原因和时间。
- `user_roles`：用户与角色映射，仅服务端或受控管理员操作可修改。

点赞数和已通过评论数可在首阶段通过受控 RPC 原子维护，避免客户端直接更新计数。

## 9. 状态与审核规则

游记状态转换：

`draft → pending_review → approved`
`pending_review → rejected → pending_review`
`approved → pending_review`（作者编辑）
`任意作者可管理状态 → deleted`（软删除）

规则：

- 普通用户不能直接写入 `approved` 或 `rejected`。
- 提交审核前必须拥有 1–9 张有效图片及完整必填字段。
- 管理员审核只能通过专用 API/RPC 执行。
- 驳回必须包含 1–500 字原因。
- 删除先软删除，图片进入延迟清理队列，避免数据库与对象存储不一致。
- 已删除和未通过内容不出现在公开接口。

## 10. 图片存储方案

使用私有 Supabase Storage bucket，例如 `community-media`。

- 路径按用户和游记隔离：`{user_id}/{note_id}/{image_id}`。
- 浏览器使用当前用户身份上传，只能操作自己的目录。
- 接受 JPEG、PNG 和 WebP；单张原始文件建议不超过 10 MB。
- 上传前将长边压缩到不超过 2048 像素，并生成适合瀑布流的封面缩略图。
- 数据库保存路径和尺寸，不保存长期公开 URL。
- 后端为草稿作者、管理员或公开已通过内容签发短期读取 URL。
- 删除游记后异步清理图片；清理失败可重试并记录。

## 11. API 边界

公开接口：

- `GET /api/community/notes`
- `GET /api/community/notes/{note_id}`
- `GET /api/community/creators/{creator_slug}`

认证接口：

- `POST /api/community/notes`
- `PUT /api/community/notes/{note_id}`
- `POST /api/community/notes/{note_id}/submit`
- `DELETE /api/community/notes/{note_id}`
- `GET /api/me/travel-notes`
- 点赞、收藏、评论和举报接口

管理员接口：

- `GET /api/admin/community/review-queue`
- `POST /api/admin/community/reviews/{target_type}/{target_id}/approve`
- `POST /api/admin/community/reviews/{target_type}/{target_id}/reject`

公开响应只返回页面需要的投影。客户端不得提交作者 ID、审核人 ID、公开状态或计数值。

## 12. 权限、安全与隐私

- 所有新表启用 RLS。
- 作者只能读取和管理自己的非公开游记及图片。
- 匿名用户只通过白名单公开接口读取已通过内容。
- 关联行程必须在数据库内验证属于当前用户，公开响应不返回私有行程 ID。
- 管理员角色由服务端和数据库共同校验，普通用户不能通过请求体伪造。
- 图片、标题、正文、评论和审核原因均限制长度和类型。
- 前端只使用安全 DOM API 渲染用户文本。
- 日志不记录 access token、邮箱、原始图片 URL、正文全文或用户 UUID。
- 举报和审核记录保留必要审计信息，但不公开给普通浏览者。

## 13. 分阶段路线图

### 阶段一：图文社区闭环

- 瀑布流首页、分类筛选、标题/地点搜索。
- 图文游记创建、草稿、预览、提交和人工审核。
- 详情页、点赞、收藏、评论和举报。
- 我的游记、只读作者主页和管理员审核页。
- Supabase Storage、RLS、公开投影和图片清理。

阶段一验收通过后再进入阶段二。

### 阶段二：关注与通知

- 关注/取消关注作者。
- “我关注的人”内容流。
- 站内通知：审核结果、评论、点赞和新增关注。
- 通知已读状态和频率控制。

### 阶段三：私信

- 双方会话、消息发送和已读状态。
- 拉黑、举报和会话级权限。
- 反骚扰限频与敏感内容治理。

### 阶段四：推荐与审核提效

- 热门排序和个性化推荐。
- 自由标签与相关内容推荐。
- AI 辅助审核，仅作为人工审核的风险提示，不直接替代最终决定。

关注、通知和私信不与阶段一同步开发。

## 14. 首阶段非目标

- 视频上传和播放。
- 直播、群聊和私信。
- 关注流和消息通知。
- 个性化推荐算法和热门榜单。
- 富文本编辑器。
- 自由标签和地图式内容发现。
- 完整运营后台、批量审核和自动审核。
- 商业推广、广告和付费内容。

## 15. 验收标准

- 匿名用户可以浏览审核通过的瀑布流和详情，不能看到草稿、待审核或驳回内容。
- 登录用户可以创建包含 1–9 张图片的独立游记，不需要先创建行程。
- 作者可以保存草稿、提交审核，并查看审核状态和驳回原因。
- 管理员可以通过独立审核页审核游记和评论，普通用户无法调用管理员操作。
- 分类筛选和标题/地点搜索返回稳定结果，分页不重复、不遗漏。
- 点赞、收藏不能重复；收藏关系不公开。
- 评论审核通过后才对其他用户显示。
- 公开响应和日志不包含邮箱、用户 UUID、原始存储路径、审核备注或私有行程数据。
- 桌面、平板和手机分别呈现四列、两列和单列内容布局。
- 旧 `community_posts` 数据仍然存在，但不会出现在新版社区。
- 后端、前端、RLS、Storage 权限和双账户隔离测试全部通过。

## 16. 成功指标与风险

首阶段优先观察：

- 游记提交成功率和图片上传失败率。
- 待审核内容平均等待时间。
- 审核通过率及主要驳回原因。
- 社区卡片到详情的点击率。
- 点赞、收藏和评论的参与率。
- 每周新增游记数和有发布行为的创作者数。

主要风险及控制：

- 图片存储和流量增长：前端压缩、缩略图、分页和缓存。
- 人工审核积压：显示等待状态、审核队列排序、后续引入 AI 风险提示。
- 冷启动内容不足：上线前准备一批经过审核的真实示例游记。
- 违规图片通过外链传播：使用私有 bucket 和短期 URL。
- 新旧社区混淆：新版接口和页面只读取 `travel_notes`，旧数据明确归档。

## 17. 实施约束

- 本策划书只确认产品和架构方向，不代表授权修改代码、提交、推送或部署。
- 下一步应单独编写可分批验收的实施计划。
- 阶段一完成并验收后，才能启动阶段二；各阶段不并行实施。
