# RAG V2 Stage 10C-1 Live Acceptance Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]` syntax for tracking).

**Goal:** Build a small operator-only live-acceptance workflow that validates the real RAG V2 corpus, Jina embeddings, active-corpus retrieval, isolated incremental reuse, and manual production activation without changing normal runtime behavior.

**Architecture:** `app/scripts/rag_v2_acceptance.py` is a thin argparse adapter over module-local `app/rag_v2/acceptance.py`. Authoring parsing is isolated in `app/rag_v2/authoring.py`; it produces existing Stage 10B domain values, while acceptance orchestration composes the existing importer, repository, passage/query embedders, retrieval service, and evaluator. Retrieval remains active-corpus-only, so production retrieval acceptance runs only after the human-approved production activation.

**Tech Stack:** Python 3.13, Pydantic 2, PyYAML, httpx, Supabase Python client, existing RAG V2 domain/repository seams, argparse, JSON/JSONL, pytest for offline tests only.

**Spec:** `docs/superpowers/specs/2026-09-04-rag-v2-stage10c-1-design.md`

## Global Constraints

- Stage 10C-1 owns live infrastructure, corpus preparation, and retrieval acceptance; Planner/runtime/API/frontend integration belongs to Stage 10C-2.
- `RagV2Repository.match_chunks(...)` retrieves the active corpus for a dataset; no staging-aware retrieval RPC, staging repository method, temporary public API, or `supabase/migrations/015_rag_v2.sql` is added.
- Production order is `production staging import → authoritative readiness=True → activation-preview → explicit ACTIVATE → production activation → required retrieval acceptance against active corpus → post-activation smoke`.
- Smoke and acceptance activations are isolated dataset operations and are never production activation or production runtime data.
- Only the explicit `activate` command may call `RagV2Repository.activate_corpus(...)`; import, preflight, preview, retrieval, and post-smoke commands cannot call it.
- Production authoring contains only Xiamen `350200/prefecture_city`, Fuzhou `350100/prefecture_city`, and Dali `532900/autonomous_prefecture`; the artificial incremental patch never enters production history.
- Program-derived `chunk_key`, `content_hash`, `embedding_input_hash`, `metadata_hash`, `manifest_hash`, `embedding`, and final `ChunkRow` values are generated by existing Stage 10B owners.
- The fixed passage profile is `jina-embeddings-v3`, `retrieval.passage`, `1024`, `rag-v2-embedding-input-v1`; the fixed query profile is `jina-embeddings-v3`, `retrieval.query`, `1024`.
- `JINA_API_KEY`, Supabase service-role credentials, authorization headers, provider response bodies, and raw secret-bearing exceptions never appear in terminal output or JSON reports; credential state is only `SET` or `MISSING`.
- `014_rag_v2.sql` is verified through live checks but is not modified, executed, or repaired by acceptance tooling.
- No automatic activation, migration, retry subsystem, rollback subsystem, background orchestration, public endpoint, runtime feature flag, enterprise approval workflow, or root export expansion is introduced.
- Codex writes diffs and static checks only; the human runs each exact PowerShell pytest command and supplies raw output before the next implementation or commit gate.
