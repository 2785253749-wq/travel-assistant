# RAG V2 Stage 10B-3 Retrieval Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement the approved Stage 10B-3 query embedding and deterministic retrieval orchestration boundary without changing the Stage 10B-2 repository/database contract or wiring Planner/runtime.

**Architecture:** A thin V2 Query Embedder converts an already-normalized query into one validated 1024-dimensional `retrieval.query` vector. A thin Retrieval Service owns normalization, calls the frozen repository candidate RPC seam, applies stable threshold/dedup/diversity/final limiting, and returns immutable retrieval evidence/result values.

**Tech Stack:** Python 3.13, pytest, existing application AppError infrastructure, existing Jina provider transport where appropriate, RAG V2 repository/domain contracts.

**Spec:** `docs/superpowers/specs/2026-09-02-rag-v2-stage10b-3-design.md`

- Query normalization owner: Retrieval Service only.
- The Query Embedder receives an already-normalized, non-empty string and never strips, lowercases, collapses whitespace, rewrites, expands, or appends destination metadata.
- Query profile: model jina-embeddings-v3, task retrieval.query, dimensions 1024.
- A successful query embedding is exactly 1024 finite floats returned as tuple[float, ...].
- Provider, legacy Jina, HTTP, network, timeout, malformed-response, missing-vector, wrong-dimension, non-numeric, boolean, NaN, and infinity failures map to code RAG_V2_EMBEDDING_UNAVAILABLE with message RAG V2 embedding is unavailable.
- An already-created AppError with code RAG_V2_EMBEDDING_UNAVAILABLE may be re-raised unchanged.
- Repository AppError values are outside the Query Embedder catch boundary and are preserved unchanged by Retrieval Service.
- candidate_k defaults to 40, is an UNVALIDATED DEFAULT, is forwarded unchanged, and is not Python-validated against 1..200.
- final_k defaults to 6, is a strict Python int, rejects bool, and requires final_k >= 1.
- score_threshold defaults to 0.70, accepts Python int or float except bool, converts to float, requires finiteness, and has no [0, 1] restriction.
- Invalid final_k always raises ValueError("final_k must be at least 1").
- Invalid score_threshold always raises ValueError("score_threshold must be finite").
- Threshold eligibility is candidate.score >= score_threshold; equality is retained.
- Selection order is threshold -> first-occurrence content_hash dedup -> diversity round 1 -> diversity round 2 -> final_k -> RetrievalEvidence mapping.
- The repository/RPC order is authoritative. Retrieval never sorts, reverses, shuffles, or recomputes scores in Python.
- Deduplication identity is content_hash only; the first occurrence wins.
- Round 1 selects at most one candidate per attraction_id in current order.
- Round 2 traverses non-round-1 candidates in original order, permits repeated attraction_id, and fills until final_k or exhaustion.
- RetrievalEvidence has exactly ten fields and excludes corpus_version_id.
- RetrievalResult has exactly query and evidence.
- Empty valid retrievals return RetrievalResult(query=normalized_query, evidence=()).
- Provider failure and persistence failure remain distinct public boundaries.
- app/rag_v2/__init__.py keeps the frozen 44-name root export surface unchanged.
- app/rag_v2/repository.py remains unchanged.
- supabase/migrations/014_rag_v2.sql remains unchanged.
- Legacy app/rag callers and behavior remain unchanged.
- Planner/runtime wiring is not added.
- Stage 10B-4 corpus import, document embedding, incremental reuse, and reuse read seams are not started.
- Live Jina, Supabase, PostgreSQL, active-corpus, vector-cast, and online-quality acceptance are not part of Stage 10B-3.

### Jina adaptation boundary

The current JinaEmbeddingTransport constructor accepts api_key, model,
timeout_seconds, and an optional HTTP client. Its embed method accepts
list[str] and sends the legacy payload containing model and input. The
existing transport validates the response shape data -> indexed embedding
lists and returns list[list[float]], but it does not send a task field.

Because the V2 query contract requires task = retrieval.query, Task 1 must
not call the legacy document-oriented transport and pretend it is a query
adapter. It must not alter the legacy module. The new V2 module may reuse the
existing Jina URL, HTTPX post/raise_for_status conventions, timeout checks,
and safe logging pattern. A private V2 Jina provider in the new module sends
one query with model, task, dimensions, and input, then returns decoded JSON
to the V2 Query Embedder. The embedder owns final response-shape and vector
validation.

The provider test double records keyword arguments:

    {
        "query": query,
        "model": model,
        "task": task,
        "dimensions": dimensions,
    }

and returns the existing Jina-style payload:

    {
        "data": [
            {"index": 0, "embedding": [1024 numeric values]},
        ],
    }

No real API key, HTTP endpoint, Supabase client, or network is used by the
unit tests.

    class RetrievalService:
        def __init__(
            self,
            *,
            embedder: QueryEmbedder,
            repository: RagV2Repository,
        ) -> None: ...

        def retrieve(
            self,
            *,

            dataset_key: str,
            destination_code: str | None = None,
            destination_level: DestinationLevel | None = None,
            province_code: str | None = None,

The complete retrieve flow is:

    normalize query
        -> embed_query(normalized_query)
        -> repository.match_chunks(...)
        -> threshold
        -> content_hash deduplication
        -> diversity round 1
        -> diversity round 2
        -> final_k
        -> RetrievalEvidence
        -> RetrievalResult

The repository call is exactly:

    repository.match_chunks(
        dataset_key=dataset_key,
        query_embedding=query_vector,

        attraction_id=attraction_id,
        candidate_k=candidate_k,
    )

The service sends normalized_query to the embedder exactly once and passes the
returned tuple unchanged to the repository. It retains score equality,
rejects only lower scores, deduplicates by first content_hash, applies both
stable diversity rounds, limits to final_k, and maps exactly the ten
RetrievalEvidence fields. There is no Python sorting, score recomputation,
threshold clamp, candidate range validation, destination inference, LLM
rewrite, or ranking framework.

          candidate

      seen_hashes: set[str] = set()
      deduplicated: list[RagV2Candidate] = []
      for candidate in thresholded:
          if candidate.content_hash in seen_hashes:

          seen_hashes.add(candidate.content_hash)
          deduplicated.append(candidate)

  Use index-based two-round selection so remaining means not selected in
  round 1:

      selected: list[RagV2Candidate] = []
      selected_indexes: set[int] = set()
      seen_attractions: set[UUID] = set()

      for index, candidate in enumerate(deduplicated):
          if candidate.attraction_id in seen_attractions:
              continue
          seen_attractions.add(candidate.attraction_id)
          selected.append(candidate)
          selected_indexes.add(index)
          if len(selected) == final_k:
              break

      if len(selected) < final_k:
          for index, candidate in enumerate(deduplicated):
              if index in selected_indexes:
                  continue
              selected.append(candidate)
              if len(selected) == final_k:
                  break
